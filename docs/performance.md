# 操作応答と UI の構成

## 方針

Root が全画面の親となり、Mediator が操作を裁定する。
View は Presenter が渡す描画モデルを表示し、意図をイベントとして返す。
Presenter はデータ取得、派生値、編集状態を管理する。
イベントは発生元のスコープから親へたどり、処理可能なスコープが引き受ける。
Mediator はダイアログ、通常操作、非同期処理の状態を区別し、背後の画面への誤操作と同一操作の重複実行を防ぐ。

共有・バックアップ機能は追加しない。
Markdown/TOML ファイルを正とし、ブラウザのキャッシュは現在のタブの操作を高速化するためだけに使う。
外部編集と文書の revision による競合検出は維持する。

## 確認した問題

- 一覧の各行で全 Issue を走査し、子 Issue 数を求めていた。
- Shell、ルート loader、詳細画面が同じ参照データを個別に取得していた。
- Project と Cycle の loader に逐次リクエストがあった。
- 複数の window keydown リスナーが同じキーに反応していた。
- Markdown のパーサ生成と HTML 生成をレンダーごとに実行していた。
- 文書と AI の定期取得が遅いレスポンス時に重複し得た。

## 採用する対策

GET の実行中リクエストと短期間の結果を共有し、変更時にキャッシュ全体を無効化する。
更新前に開始したリクエストが更新後のキャッシュを上書きしないよう世代を管理する。
Issue の状態・優先度・並び順は通信完了前に表示へ反映し、失敗時に戻す。
一覧は可視範囲と余白だけを描画し、選択移動時に対象行を表示する。
行内の集計は一度の走査で作る。
重い文書・補助画面は必要時に読み込む。
動きは短い transform / opacity に限定し、選択・入力・閉じる操作を待たせない。
prefers-reduced-motion、IME、フォーカス復帰、ダイアログ内の Tab 循環を検証する。

## 代替案と制約

IndexedDB に全ワークスペースを複製する案は、外部編集との整合性と移行の負担が大きいため採用しない。
単純な React.memo の追加だけでは、重複取得と二重キー処理を解消できない。
Root の単一巨大 React state は全画面の再描画を招くため、操作の裁定は中央に置き、表示の購読は分離する。

キャッシュ中は外部編集の反映にポーリング間隔分の遅延がある。
文書保存はサーバーの revision 検査を通すため、競合を表示速度のために無視しない。
性能測定は同一 Chromium・同一データの変更前後比較とし、実環境の絶対的な応答時間の保証には使わない。
一覧の DOM 件数、重複取得数、操作の即時反映は回帰テストで固定する。

## 検証

[Linear の技術解説](https://performance.dev/how-is-linear-so-fast-a-technical-breakdown)を参考に、タブ内キャッシュ、楽観的更新、描画量の制限を優先した。
Chromium、1440 × 900、5,000 Issue の同じモック API を用いた単回の比較では、一覧表示が 694 ms → 223 ms、一覧から Board への遷移が 796 ms → 80 ms となった。
描画する Issue 行は 5,000 → 28、DOM ノードは 25,109 → 216、API リクエストは 29 → 13 に減った。
測定スクリプトは `web/scripts/measure.mjs`。
時間値はブラウザ側の参考値であり、実ファイル読み込みの改善や統計的な保証を示すものではない。
サーバーのファイル走査とキャッシュ全体の無効化には今後の改善余地がある。

Playwright では実サーバーを使う作成・編集・競合・ACP 操作に加え、大規模一覧、楽観的更新の失敗復元、IME、フォーカス、reduced motion を検証する。
入力欄は Enter で改行、Ctrl/⌘+Enter で送信・作成する。
AI 入力と作成ダイアログのキー入力、作成ボタンとの二重実行防止も E2E に含める。
