# Design Doc

Design Doc の目的は、実装前に不確実性を可視化し、手戻りを減らせる範囲で解消することである。完璧な予測や固定テンプレートを求めない。

kotowari では置き場は **Page** である。決定の証拠が要る話は Design Doc で終わらせず ablation skill へ渡す。既に決まった短い記録だけなら Design Doc を書かない。

## 必須の 3 点

提案を結論だけで終わらせない。独立した節にするか既存フォーマットへ統合するかは文書に合わせる。

### 代替案

実際に採用可能な選択肢と比較基準を示す。各案について、満たす要件、利点、コスト、失う性質、却下理由を判断に必要な粒度で書く。現状維持が現実的なら、それも候補に含める。数を増やすためだけの案や、最初から成立しない案を水増ししない。

選択した案がどのトレードオフを受け入れた結果なのかを明記する。

### 懸念点

案を選んだ後にも残るリスクと、作成者だけでは解消できず助けが必要な未知を記す。代替案の却下理由とは分ける。

### 未決定事項

今は決めない事項について、少なくとも次を示す。

- 何を決める必要があるか
- なぜ今は決めないのか
- いつ、誰またはどの役割が決めるのか
- 判断に必要な情報や先行条件
- 未決定のまま実装へ進めるか、開始を止めるブロッカーか

「後で決める」だけで終わらせない。承認後に追跡する仕事は Issue（ISS）へ落とす。

## 調査と根拠

既存の文書、実装、制約を先に確認する。確認できない情報を自然な仮定で埋めず、意思決定に影響するものは懸念点または未決定事項として扱う。
